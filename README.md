# AI Dungeon Master

A solo roleplaying app with a future AI Dungeon Master. **The Archive** turns uploaded books into searchable knowledge. **The Chronicle** stores character sheets, story events, NPC memory, and a full campaign roadmap generated by a local model.

## Run locally

Use Python 3.12–3.14 (tested with 3.12). No Node.js, Docker, paid API, or API key is required. Book indexing runs on the CPU; optional campaign planning uses a local Ollama model.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m dungeon_master
```

Open **http://127.0.0.1:8000** for the game home screen. Choose a campaign save, continue the last campaign opened in this browser, or start a new campaign from an indexed adventure. Each save card shows the saved character, class, level, source adventure, and last saved time.

**Upload Materials** (`/materials`) contains separate **Rules** and **Campaign Books** areas. Upload a book or try a sample, wait for **Ready for retrieval**, then use **Find a passage** to verify the index. **View passages** shows the extracted text and its source location.

**Campaign Docs** (`/campaign-docs`) groups character sheets, campaign logs, relationships, and the DM plan by campaign. Search by campaign or character name, open a specific document for editing, or download player documents as PDF, Markdown, or JSON. DM plans retain their explicit spoiler gate. Document and play links carry the campaign ID, so they open the intended save regardless of the last campaign selected in this browser.

Choose **Delete** on a save card or campaign folio to remove a campaign. The confirmation names the campaign and explains that its character, log, NPC memory, plan/history, rolls, battle map, and private alignment records are permanently removed together. Uploaded books and their search indexes stay in Materials, and other saves are unaffected. The deleting browser also clears the campaign's artwork and map preference. A running local AI call may finish, but its result is discarded once the campaign is gone.

## Two source collections

- **Rules:** rulebooks, combat and spell references, character options, and house rules.
- **Campaigns:** adventure books, settings, locations, NPCs, and campaign notes.

Each collection has its own upload area, book list, indexing progress, and retrieval scope. Search **Rules only**, **Campaigns only**, or **Rules + Campaigns**; optionally narrow further to one book. Both semantic and keyword retrieval apply the selected collection before ranking. Returned passages and context identify the collection alongside the source citation.

Duplicate detection is per collection: the same file can be indexed in both collections, while repeated uploads within one collection reuse the existing book. Use **Move to Rules / Campaigns** to change a finished book's collection without regenerating its embeddings. If the destination already contains that file, the move is rejected and both existing entries are preserved.

Existing libraries upgrade automatically. Earlier uploads are placed under Campaigns and keep their original IDs, passages, vectors, and source files. Move any rulebooks into Rules as needed. The pre-upgrade database is backed up to `data/library.before-collections.sqlite3` before the transactional migration.

The first upload downloads the English `BAAI/bge-small-en-v1.5` embedding model, approximately 70 MB, from Hugging Face. Subsequent processing uses the cached model. Book contents and queries are processed locally. You can download the model ahead of time:

```sh
python -m dungeon_master --prepare-model
```

The tested dependency versions, including test tools, are recorded in `requirements.lock.txt`. To reproduce them in a clean Python 3.12 environment:

```sh
python -m pip install -r requirements.lock.txt
python -m pip install --no-deps -e .
```

## Selectable rulebook sets

In **Upload Materials → Rulebook sets → Create a set**, name a group and check the indexed rulebooks it should include. A set can hold 1–50 books; a book can belong to several sets. For example, “Core Rules” can combine a player handbook, DM guide, and monster book. Grouping reuses the original passages and embeddings.

Choose the set in **New campaign**, or change an existing save through **Rulebook set** in the play sidebar or Campaign Docs. Saves retain their selected set across restarts. The home screen and campaign folios show its name. **Edit set** changes its name or membership for every campaign using it; revision checks reject stale edits.

**Search this set** searches its member rulebooks together. Both semantic and keyword candidates are filtered before ranking. Deleted, moved, or reindexing members mark affected sets as needing attention; incomplete sets cannot be selected or searched until repaired. Searches never fall back to unrelated books. Deleting a campaign keeps these reusable sets and their books.

The API supports `GET /api/rule-sets`, `POST /api/rule-sets` with `{name, book_ids}`, and `PUT /api/rule-sets/{id}` with `{name, book_ids, expected_revision}`. IDs are UUIDs; names must be unique. `POST /api/campaigns` optionally accepts `rule_set_id`. For an existing save, `PUT /api/campaigns/{id}/rules` accepts `{rule_set_id, expected_rule_set_id}`; either value can be `null`, and both are required to protect against conflicting selections.

`POST /api/retrieve` accepts either `rule_set_id` for only that set's rules, or `campaign_id` for that save's source adventure and chosen rules. Existing `collection` and `book_id` filters narrow this scope further. A campaign with no selected set searches no rulebooks. An unavailable selected set returns 409 instead of widening the scope; requesting a book outside the scope returns 400. DM context includes the selected set and a `retrieval_scope` object for the future gameplay loop. Live AI chat remains a future milestone.

## What “ragified” means here

1. **Store:** validate the upload, save its Rules/Campaigns collection, and store the original file with a generated filename. SHA-256 deduplicates identical uploads within the selected collection, including files renamed by the user.
2. **Extract:** read PDF pages, EPUB sections in spine order, or UTF-8 / BOM-marked UTF-16 text. PDF citations use physical, one-based PDF page numbers, which may differ from printed page numbers.
3. **Chunk:** normalize text and split it into overlapping passages, bounded by the source page or section. Each passage fits within 360 tokens of the actual embedding tokenizer. Paragraph and sentence boundaries are preferred; short chunks use proportionally smaller overlaps.
4. **Embed:** generate normalized, 384-dimensional vectors locally with FastEmbed / ONNX on the CPU.
5. **Index:** atomically commit passages, vectors, source references, model identity, and a full-text index to SQLite. A book only becomes searchable once the entire index is ready.
6. **Retrieve:** combine cosine similarity and SQLite FTS5 keyword search with reciprocal rank fusion. Return excerpts, stable book IDs, chunk IDs, source labels, and a citation-labeled context string for the future DM.

The app includes background processing, persistent status/progress, warnings for PDF pages without readable text, retries/reindexing, passage previews with pagination, per-book search, and deletion of the original file and its index. Interrupted jobs resume from the beginning on server restart.

The app now includes local campaign planning and persistent game records. Live DM gameplay/chat, multiplayer, and accounts remain future milestones. During development you can edit records in the UI and use the atomic turn API for DM integration.

## Campaign records and downloads

Choose **Load campaign** from Home to open its play table, or choose a record in **Campaign Docs**. **New campaign** on Home creates a save from a fully indexed adventure in the Campaign Books collection and opens its character sheet. `/campaigns?campaign={id}` links directly to a save; add `&docs=character`, `log`, `relationships`, or `plan` to open a particular document. A missing campaign ID shows an unavailable-save message instead of silently opening another campaign. Each campaign keeps independent records:

The campaign table puts a collapsible battle map above the story journal, with a fixed character sidebar for HP, AC, speed, abilities, trained skills, weapons, inventory, and the latest recorded world time. **Campaign docs** opens the complete records and downloads without leaving the table. The composer currently saves journal entries; AI conversation is a future step. Ctrl/Cmd + Enter also saves an entry.

Optional character portraits accept PNG, JPEG, or WebP up to 8 MB and stay in the current browser. Map visibility preferences also stay in this browser. Tactical maps, journal entries, and character records use the canonical SQLite campaign store. Character edits preview in the sidebar and remain marked as an unsaved draft until saved in Docs.

- **Character sheet:** identity, six ability scores, derived modifiers, all 18 skills, saves, HP, armor, initiative, speed, proficiency, hit dice, death saves, conditions, spells/slots, equipment, backstory, traits, and notes. Private character notes are excluded from player copies. Revision checks prevent an open form from overwriting newer character updates.
- **Campaign log:** ordered session events with timestamps, choices, discoveries, combat, loot, and the full scene/details. Hidden DM events stay out of player copies. Events are append-only; the story log is separate from the generated plan.
- **NPC relationships:** disposition, trust, feelings, public notes, private motives, and individual facts the NPC knows about the player. Each fact states how it was learned and can reference a log event. Facts from another campaign are rejected. Player copies include only known NPCs, revealed knowledge, and explicitly revealed feelings.
- **DM campaign plan:** an ordered, branching outline from the opening to possible endings, with scene options, completion conditions, source references, progress states, and reading coverage. This is an AI-generated proposal; verify established facts against the source adventure. Future possibilities never become story history merely because they appear in the plan.

Character sheets, logs, and relationship records download as **PDF, Markdown, or JSON**. The plan has a separate **DM-only export** behind an explicit spoiler view. Download links read current saved state, so they reflect edits and recorded turns. Campaign data and plan history are stored in `library.sqlite3`; back it up with the rest of `data/`.

This remains a local, single-user application. The DM/player split prevents accidental spoilers in normal views and exports; it is not an authentication boundary against the person who owns the local server. Do not expose this app as a shared service without adding authorization.

### Player d20 rolls

Every requested player roll appears at the table with its reason, `1d20` formula, modifier, and a **Roll d20** button. The die animates on screen only after the player presses it, then shows the raw face and total. Results remain in the campaign log and downloads; **View roll** reopens a saved result. Reduced-motion preferences disable the tumble animation.

The **Roll d20** shortcut handles the next pending check, or makes a free roll if none is waiting. **Campaign docs → Campaign log → Request a player d20 roll** can queue a check manually. Live AI conversation remains a future milestone; its turn contract can already queue these same buttons:

```json
{
  "event": {"title": "The narrow bridge", "summary": "A rope bridge crosses the chasm."},
  "roll_requests": [{
    "label": "Dexterity check",
    "reason": "Keep your balance while crossing the narrow bridge.",
    "modifier": 3
  }]
}
```

Submit that to `POST /api/campaigns/{id}/turns`. Requests commit atomically with the scene. Labels and reasons are public, so keep hidden information out of them. The future DM must wait for the matching stored result before resolving that action. It must not invent a dice value or substitute an unrelated free roll.

`POST /api/campaigns/{id}/rolls` also queues a request; reuse its `idempotency_key` when retrying creation. `POST /api/campaigns/{id}/rolls/{roll_id}/roll` accepts an empty body and generates an unbiased integer from 1 to 20 with Python's local `secrets` generator. The modifier is fixed when requested. Roll resolution and its log event commit together; repeat or concurrent presses return that same saved result. Pending checks and completed results survive restarts. Rolls do not automatically change HP or adjudicate success, failure, or critical outcomes.

### Tactical battle map

The table's **Battle map** opens a lightweight SVG tactical sketch. **Load starter encounter** creates an illustrative outpost with walls, a door, cover, difficult terrain, water, hazards, and five named circular tokens. **Setup** also offers an empty grid, configurable dimensions from 10–30 squares per side, token placement/removal, door controls, and a combat toggle. The template is a practice layout, not an encounter inferred from the uploaded adventure.

Each square is 5 feet. Blue tokens are players, green allies, red enemies, and gray neutrals. Names shrink or abbreviate to fit; hover or select a token to read its full name. Selection also shows available HP, conditions, and remaining movement. Drag onto a square, select then click a destination, or use arrow keys on a focused token. Zoom, fit, and expand controls support larger boards. Collapsing the map keeps its state; positions and encounter data survive reloads and server restarts.

The renderer receives structured state from the campaign store and owns only selection, zoom, and temporary drag visuals. Backend and future AI turns use the same validated contract. Read `GET /api/campaigns/{id}/battle` for `{state, revision, updated_at}`, then create or replace a map with `PUT /api/campaigns/{id}/battle`:

```json
{
  "expected_revision": 0,
  "state": {
    "title": "The broken gate",
    "map": {
      "width": 10, "height": 10, "feet_per_cell": 5,
      "terrain": [{"x": 5, "y": 3, "kind": "obstacle"}],
      "walls": [{"x1": 1, "y1": 1, "x2": 9, "y2": 1}],
      "doors": [{"id": "gate", "x1": 4, "y1": 1, "x2": 5, "y2": 1, "open": false}]
    },
    "tokens": [
      {"id": "pc_1", "name": "Adventurer", "faction": "player", "character_ref": "player", "x": 4, "y": 8},
      {"id": "enemy_1", "name": "Goblin 1", "faction": "enemy", "x": 3, "y": 2, "hp_current": 7, "hp_max": 7}
    ],
    "combat": {"active": true, "round": 1, "active_token_id": "pc_1"}
  }
}
```

API cell coordinates are **zero-based**; labels and placement controls in the UI are one-based. Wall endpoints lie on grid intersections, and each door occupies one horizontal or vertical edge. Unlisted cells are open floor. Terrain kinds are `floor`, `difficult`, `water`, `hazard`, and `obstacle`. API boards support 3–40 squares per side and up to 100 tokens. Token IDs are stable identifiers independent of names; multiple creatures may share a displayed name.

Patch existing state with `PATCH /api/campaigns/{id}/battle`, using the revision returned by the last read or write:

```json
{
  "expected_revision": 1,
  "move_tokens": [{"id": "enemy_1", "x": 4, "y": 2}],
  "spawn_tokens": [{"id": "ally_1", "name": "Guard", "faction": "ally", "x": 3, "y": 8}],
  "token_updates": [{"id": "enemy_1", "conditions": ["Prone"], "movement_remaining": 15}],
  "door_updates": [{"id": "gate", "open": true}],
  "combat": {"active": true, "round": 2, "active_token_id": "enemy_1"}
}
```

`remove_tokens` accepts token IDs; `map` replaces the complete grid geometry while retaining tokens. A full `state` replacement cannot be mixed with patches. Writes validate the final state atomically: tokens must be in bounds, on distinct squares, and outside obstacles; active combat tokens must exist. A stale revision returns 409 without overwriting newer state. Invalid edits return 422 and preserve the previous map. Removing the active token clears its turn marker.

Both player snapshots and DM context include `battle`. A future DM can include the same change object as `battle_update` in `/turns`, committing the map together with narration, character changes, roll requests, and NPC memory. Reuse the turn's idempotency key on retries. Keep **all map fields player-visible**, including token notes and combat notes. A token linked with `character_ref: "player"` reads name, HP, and conditions from the saved character sheet; change these through the character API or `character_changes`, rather than creating a second copy on the token.

This is a positioning aid: moves do not calculate paths, prevent crossing walls or closed doors, spend movement, apply terrain damage, or adjudicate combat. There is no fog, line of sight, image generation, portrait token art, or freeform narrative parsing. The live AI chat loop remains a future milestone; structured map creation and updates already work through the backend.

### Private alignment memory

Alignment is hidden from the character editor, player campaign state, and player PDF, Markdown, and JSON downloads. It is descriptive DM background memory, not a choice during character creation or a restriction on actions. Existing alignment values migrate into private memory.

Reaching a new highest character level, through either a sheet save or an atomic turn, queues a local Ollama review. The review reads every newly logged event through that level-up, including the triggering turn. It scores only evidenced actions by the player character on order and care axes (-2 to +2), keeps a cumulative average, and derives the nine alignment tendencies at thresholds of ±0.5. Neutral or unclear axes score zero; no evidence preserves the previous tendency. New characters remain undetermined until there is evidence. This is this app's background mechanic, not a rulebook requirement.

Ordinary actions and sheet edits do not change alignment between level-ups. Level decreases, repeat saves, and retried turns cannot rescore a milestone. Multiple pending milestones run in order; evidence added after a level-up waits for the next milestone. Reviews and their cited event IDs stay in DM context and explicit DM character exports. The AI must not reveal them during play. Only actual log events are reviewed, never campaign book proposals or character identity traits.

Reviews persist across restarts. If Ollama is unavailable or returns invalid evidence, the level-up still saves and the previous tendency remains. Restarting the app retries unfinished reviews; `POST /api/campaigns/{id}/alignment/retry` also retries them after local model setup. A failed review blocks later reviews until it succeeds, preserving the action history.

### Local campaign planning with Ollama

Install [Ollama](https://ollama.com/download) first (on macOS, `brew install ollama`). In one terminal, start it using the project's model directory, with cloud access disabled:

```sh
OLLAMA_NO_CLOUD=1 OLLAMA_MODELS="$PWD/data/models/ollama" ollama serve
```

In another terminal:

```sh
ollama pull qwen3:4b
.venv/bin/python -m dungeon_master
```

The default `qwen3:4b` model downloads about 2.5 GB. It was tested locally on a 16 GB Apple Silicon Mac. Set `DM_PLANNING_MODEL` to choose another installed local model; `DM_OLLAMA_URL` defaults to `http://127.0.0.1:11434` and must remain a loopback HTTP address. The app uses Ollama's [structured-output API](https://docs.ollama.com/capabilities/structured-outputs); it never calls a cloud generation API. Do not configure a cloud-backed Ollama model when you want local-only processing.

Creating a campaign automatically queues planning. The planner snapshots **every indexed source passage**, reads the entire adventure in bounded sections, checkpoints section summaries, reduces long books' notes, and synthesizes the full outline. It does not replace a full reading with top-k search. It reports coverage, rejects invented source IDs, retains the previous plan if a retry fails, and stores successful versions in plan history. Interrupted jobs resume using saved reading checkpoints. If Ollama is unavailable, records still work and the plan shows **needs setup** with a retry action.

Scanned/omitted source pages remain subject to the extraction limits above: planning covers the complete *indexed text*, not illustrations or unreadable scans. A local model can still misunderstand or invent details; citations and coverage do not prove factual accuracy.

### Wiring future DM turns to memory

Before choosing the next scene, read `GET /api/campaigns/{id}/dm-context`. It includes the canonical character, full log, individual NPC memories, full plan, and current/next phase. After resolving a turn, submit `POST /api/campaigns/{id}/turns`:

```json
{
  "idempotency_key": "46b9b942-4ec8-4834-b79f-38cb13cd9ccb",
  "event": {
    "title": "A conversation at the inn",
    "summary": "Elara tells Mara about the missing seal.",
    "details": "The complete narration for this resolved turn.",
    "session": 1,
    "kind": "story"
  },
  "character_changes": {"hp_current": 8},
  "npc_updates": [{
    "name": "Mara",
    "disposition": "friendly",
    "knowledge": [{"fact": "Elara seeks the seal", "learned_from": "Elara said so during this conversation"}]
  }],
  "phase_updates": [{"phase_id": "phase-1", "status": "completed"}]
}
```

The event, character patch, NPC changes, milestone updates, roll requests, and optional battle update commit in one SQLite transaction. An invalid update rolls back the whole turn. Reuse the same idempotency key when retrying a network request; it cannot create a duplicate log event. Use existing NPC IDs from DM context when updating known characters. NPC patches preserve omitted fields and accumulate learned facts; newly learned facts link to the current event automatically. Explicitly supplied evidence must belong to this campaign. Only one phase is current at a time.

The UI's event form records manual story events through this same turn API. The live play/chat loop has not yet been implemented; automatic updates during future gameplay should use this contract rather than maintaining a second copy of the records.

## Supported books and limits

| Format | Extraction | Source reference |
| --- | --- | --- |
| PDF | Embedded text, page by page | Physical PDF page |
| EPUB | DRM-free HTML chapters in the book's reading order | Section number and title |
| TXT / Markdown | UTF-8 or BOM-marked UTF-16 | Text source and passage ID |

- Default upload limit: 100 MB per file. Extracted text is limited to 20 million characters, 5,000 PDF pages, and 30,000 passages per book. EPUB expansion is also bounded.
- **Scanned/image-only books need OCR before upload.** OCR, illustrations, map understanding, and table reconstruction are outside this milestone. Mixed PDFs retain readable pages and warn about skipped pages. PDF reading order depends on the book's text layer, so inspect passages from complex layouts.
- This is a local, single-user application. Run one server worker per data directory; a process lock prevents competing ingestion workers. Authentication and shared deployments need a later service layer.
- Vectors are searched in batches with an exact scan. This suits a personal library; a large/shared library can move to pgvector or a vector service behind the retrieval layer.
- Retrieval returns the closest excerpts even when they do not answer the query. Scores are ranking signals, not confidence or proof. Check the cited source.
- Future generation should treat retrieved book text as untrusted reference material and keep DM instructions separate from source excerpts.

## Storage and settings

All runtime data is under `data/` by default and is ignored by Git. Back up the entire directory to retain books and indexes.

```text
data/
  uploads/           # Original books, stored by generated book ID
  models/            # Cached local embedding model
  library.sqlite3    # Books, job state, passages, vectors, FTS index
  server.lock        # Single-worker process lock
```

Optional shell settings (see `.env.example`; `.env` is not automatically loaded):

```sh
export DM_DATA_DIR="/path/to/my/library"
export DM_MAX_UPLOAD_MB=100
```

`DM_EMBEDDING_MODEL` defaults to `BAAI/bge-small-en-v1.5`. The pipeline is tuned for this English model and its 512-token window; replacement models must support at least that window. Changing the model marks existing books as needing reindexing, and incompatible indexes are excluded from retrieval.

Use `python -m dungeon_master --port 8001` to change the port.

## API

Interactive documentation: **http://127.0.0.1:8000/docs**.

| Method | Endpoint | Purpose |
| --- | --- | --- |
| GET | `/api/health` | Read limits, format support, and model name |
| POST | `/api/books` | Multipart fields `file` and `collection` (`rules` or `campaign`); 202 queued, 200 duplicate |
| GET | `/api/books?collection=rules` | List books in one collection; omit filter for all books |
| GET | `/api/books/{id}` | Poll a book's progress / failure details |
| PATCH | `/api/books/{id}` | Move a finished book using `{"collection":"rules"}` or `{"collection":"campaign"}` |
| GET | `/api/books/{id}/chunks?offset=0&limit=10` | Preview source passages |
| POST | `/api/books/{id}/reindex` | Retry a failed book or rebuild its index |
| DELETE | `/api/books/{id}` | Remove a finished/failed book and its index |
| POST | `/api/retrieve` | Search ready books and return source context |

```sh
curl -F 'file=@/path/to/rulebook.pdf' -F 'collection=rules' http://127.0.0.1:8000/api/books

curl -F 'file=@/path/to/adventure.pdf' -F 'collection=campaign' http://127.0.0.1:8000/api/books

curl http://127.0.0.1:8000/api/books

curl http://127.0.0.1:8000/api/retrieve \
  -H 'Content-Type: application/json' \
  -d '{"query":"How can someone cure the sick traveler?","collection":"campaign","limit":5}'
```

Set `"collection":"rules"` or `"collection":"campaign"` to scope retrieval; omit it or use `null` to search both. Add `"book_id":"<UUID returned by upload>"` to scope retrieval to one book. If both filters are supplied, the book must belong to the selected collection. Uploads without a collection default to `campaign` for compatibility with earlier clients. Each result includes `citation`, `book_id`, `chunk_id`, `collection`, `title`, `source_label`, `text`, `score`, and cosine `similarity`. The top-level `context` contains those excerpts labeled `[S1]`, `[S2]`, and so on. These are reference passages to pass to a future generation model; the service does not generate an answer.

## Verification

```sh
python -m pytest -q

# Real CPU embeddings, PDF ingestion, and paraphrased retrieval.
# Uses ./data/models; downloads the model if it is not cached.
DM_TEST_MODEL=1 python -m pytest tests/test_real_model.py -q
```

The offline tests cover PDF / EPUB extraction and ordering, unreadable/encrypted PDFs, token limits and source boundaries, per-collection duplicate detection, isolated semantic and keyword retrieval, combined search, collection moves and collisions, legacy database migration, input and size validation, atomic reindexing, restart recovery, changed model handling, and deletion of file/vector/full-text data. The opt-in test verifies real 384-dimensional embeddings and finds a medicine passage using a paraphrased query within the selected collection.
